# Redveil 면접·학습 가이드

이 문서는 Redveil 전체를 빠르게 복습하고, 데이터 분석·제품 분석 면접에서 프로젝트를 일관되게 설명하기 위한 요약본입니다.

> 핵심 질문: **서울 소형 상가를 바로 매입하기 전에, 무엇 때문에 멈추고 무엇을 다시 확인해야 하는가?**

---

## 1. 30초 프로젝트 소개

Redveil은 서울 소형 상가 매입 후보를 검토할 때 가격 부담, 거래 유동성, 가격 변동성, 점포 경쟁, 수요 취약성과 같은 위험 신호를 먼저 보여주는 지도 기반 리스크 분석 제품입니다.

좋은 투자처를 추천하거나 수익률을 예측하는 대신, 서울 25개 자치구를 같은 기준으로 비교하고 **매입을 보류해야 하는 이유**, **대체 후보**, **추가 확인 항목**을 설명합니다.

Python과 pandas로 공개 데이터를 정리하고 리스크 점수를 생성했으며, 정적 HTML·CSS·JavaScript 화면에서 지도 탐색, 매물 검토, 3분 진단, 후보 비교, 구별 리포트와 판단 메모로 연결했습니다.

## 2. 1분 면접 답변

상가 매입 데이터는 거래가격, 거래량, 상권 수요, 점포 수처럼 서로 다른 형태로 흩어져 있고, 원자료만으로는 사용자가 무엇을 조심해야 하는지 판단하기 어렵습니다.

그래서 Redveil에서는 질문을 “어디를 사야 하는가”가 아니라 “이 판단이 틀릴 수 있는 가장 강한 이유는 무엇인가”로 바꿨습니다.

거래 데이터에서는 구·월별 가격 수준, 가격 상승률, 거래량 감소, 가격 변동성과 저표본 여부를 만들었고, 상가정보에서는 점포 밀도와 음식업 비중, 업종 집중도를 계산했습니다. 각 지표는 서울 자치구 내 백분위 점수로 변환하고, 설명 가능한 가중합으로 가격 부담·유동성·변동성·경쟁 위험을 만들었습니다.

최종 결과는 숫자 하나로 끝내지 않고, 위험 사유와 대체 후보, 현장 확인 체크리스트, 판단 메모로 번역했습니다. 모델의 목적은 자동 추천이 아니라 검토 우선순위를 좁히는 1차 필터입니다.

## 3. 문제 정의

### 사용자 문제

소형 상가 매입 후보는 겉으로 매력적으로 보여도 다음 위험이 함께 존재할 수 있습니다.

- 최근 가격선 대비 과도한 매입가
- 거래량 감소와 낮은 회전성
- 적은 표본 때문에 흔들리는 가격
- 높은 점포 밀도와 유사 업종 과밀
- 유동인구 대비 낮은 매출 효율

하지만 원자료는 의사결정 언어가 아니라 행과 열로 제공됩니다. 사용자는 여러 데이터를 직접 결합해 해석하기 어렵습니다.

### Redveil의 해결 방식

Redveil은 매입 추천 대신 다음 결정을 지원합니다.

1. 자치구를 선택한다.
2. 리스크 점수와 핵심 반대 근거를 확인한다.
3. 매물 조건을 입력해 보류 사유를 만든다.
4. 가격선·보유 기간·우선순위를 반영한 빠른 진단을 수행한다.
5. 다른 자치구를 동일한 기준으로 비교한다.
6. 판단 메모와 추가 확인 항목을 남긴다.

### 프로젝트의 차별점

- 예측 정확도 경쟁보다 **설명 가능한 휴리스틱**을 택했습니다.
- “추천”보다 **보류와 재확인**을 중심에 두었습니다.
- 점수, 문장형 근거, 대체 후보, 메모를 하나의 사용자 흐름으로 연결했습니다.
- 데이터 분석 결과를 실제로 사용할 수 있는 정적 웹 제품까지 구현했습니다.

## 5. 전체 데이터 파이프라인

```text
원천 거래 데이터
  ↓ 상가 용도 필터링
구·월별 거래 요약
  ↓ 이동평균·증감률·변동성
거래 리스크 점수

상권 매출 + 유동인구
  ↓ 상권별 효율 지표
수요 취약성 점수

점포 정보
  ↓ 자치구·행정동 집계
점포 경쟁 점수

거래 리스크 + 점포 경쟁
  ↓ 최종 가중합
자치구 매입 리스크
  ↓ 문장형 근거·대체 후보
웹 공개 payload와 판단 메모
```

### 핵심 파일 흐름

| 순서 | 파일 | 역할 |
| --- | --- | --- |
| 1 | `src/redveil/pipelines/build_transaction_risk_scores.py` | 거래 데이터 집계, 시계열 파생변수, 거래 리스크 생성 |
| 2 | `src/redveil/pipelines/prepare_external_market_data.py` | 상권·점포 원천 데이터 정리, 점포 경쟁 데이터 생성 |
| 3 | `src/redveil/pipelines/build_redveil_outputs.py` | 수요 취약성, 최종 매입 리스크, 대체 후보, 메모 생성 |
| 보조 | `src/redveil/utils/scoring.py` | 백분위 점수와 0~100 범위 처리 |

## 6. 거래 리스크 분석

### 6.1 전처리와 집계

상가 목적에 가까운 건축물 용도만 남깁니다.

- 제1종근린생활
- 제2종근린생활
- 판매

이후 구·월별로 다음 값을 집계합니다.

- 거래 건수
- 거래금액 중앙값·평균
- ㎡당 가격 중앙값·평균
- 건물면적 중앙값
- 건축연도 중앙값

### 6.2 거래가 없는 월도 남긴 이유

월과 자치구의 전체 조합을 먼저 만든 뒤 집계 결과를 결합합니다.

이렇게 하면 거래가 없는 구·월이 데이터에서 사라지지 않고 거래 건수 0으로 유지됩니다. 거래가 없다는 사실 자체가 유동성 분석에서 중요한 정보이기 때문입니다.

### 6.3 평균보다 중앙값을 주요 지표로 본 이유

상가 거래는 면적, 입지, 건물 상태에 따라 금액 편차가 크고 극단값의 영향을 많이 받습니다. 중앙값은 일부 고가 거래가 지역 가격선을 과도하게 끌어올리는 문제를 줄입니다.

### 6.4 시계열 파생변수

- 3개월 ㎡당 가격 이동평균
- 6개월 ㎡당 가격 이동평균
- 3개월 거래량 이동평균
- 6개월 거래량 이동평균
- 6개월 가격 표준편차
- 현재 가격의 3개월·6개월 기준 대비 증감률
- 현재 거래량의 6개월 평균 대비 증감률

### 6.5 거래 위험 점수

#### 가격 부담

```text
가격 부담 = 가격 수준 65% + 가격 상승 35%
```

가격 자체가 높은 지역인지와 최근 기준선보다 빠르게 상승했는지를 함께 봅니다.

#### 거래 유동성

```text
유동성 위험 = 낮은 거래량 55% + 거래 감소 45%
```

현재 거래가 적은지와 평소보다 거래가 더 줄었는지를 구분해 반영합니다.

#### 가격 변동성

최근 6개월 ㎡당 가격의 표준편차를 서울 자치구 내 상대 점수로 변환합니다.

#### 전체 거래 리스크

```text
거래 리스크 = 가격 부담 50% + 유동성 위험 30% + 변동성 20%
```

## 7. 점포 경쟁과 수요 취약성

### 7.1 점포 경쟁

점포정보를 대용량 청크 단위로 읽어 자치구와 행정동별로 집계합니다.

주요 신호는 다음과 같습니다.

- 점포 밀도
- 행정동당 점포 수
- 음식업 점포 비중
- 상위 업종 집중도

공개 검증 문서의 점포 경쟁 가중치는 다음과 같습니다.

```text
점포 경쟁 = 밀집도 45% + 음식업 특화 25% + 업종 집중 30%
```

### 7.2 수요 취약성

상권 매출과 유동인구를 결합해 다음 지표를 만듭니다.

- 유동인구 대비 매출 효율
- 거래 1건당 매출
- 서비스 업종 수 대비 유동인구
- 업종 다양성
- 매우 낮은 유동인구 표본 경고

```text
수요 취약성 =
매출 효율 35%
+ 객단가 20%
+ 업종당 수요 25%
+ 업종 다양성 10%
+ 저유동인구 불안정성 10%
```

### 중요한 설명 포인트

수요 취약성은 상권 단위의 별도 분석 신호입니다. 현재 자치구 최종 매입 리스크 가중합에는 거래 리스크와 점포 경쟁이 직접 들어가며, 수요 취약성은 상권 해석과 추가 검토 맥락에 활용됩니다.

면접에서는 “모든 지표를 무조건 하나의 총점에 넣지 않고, 공간 단위가 다른 신호는 별도 해석층으로 남겼다”고 설명할 수 있습니다.

## 8. 최종 매입 리스크와 대체 후보

### 최종 자치구 매입 리스크

```text
최종 매입 리스크 = 거래 리스크 55% + 점포 경쟁 45%
```

최종 결과에는 다음 항목이 포함됩니다.

- 총 매입 리스크 점수
- 위험 등급
- 가격 부담
- 거래 유동성
- 가격 변동성
- 점포 경쟁
- 저표본 여부와 신뢰도
- 핵심 반대 근거

### 대체 후보 생성

현재 후보보다 최종 점수가 일정 수준 이상 낮은 자치구를 먼저 찾습니다.

그중에서 다음 조건을 활용해 유사한 후보를 우선합니다.

- 음식업 비중 차이가 지나치게 크지 않은가
- 유동성 위험이 현 후보보다 크게 나쁘지 않은가
- 전체 위험과 점포 경쟁의 차이가 어느 정도인가

대체 후보는 “무조건 더 좋은 투자처”가 아니라 **같은 검토 문맥에서 비교할 후보**입니다.

## 9. 왜 백분위 점수를 사용했는가

Redveil은 서로 단위가 다른 지표를 합쳐야 합니다.

- 거래 건수: 건
- 가격: 만 원 또는 ㎡당 만 원
- 변동성: 표준편차
- 점포 밀도: 점포 수 기반 비율

원 단위를 그대로 더할 수 없기 때문에 각 지표를 서울 자치구 안에서 0~100에 가까운 상대적 백분위로 변환했습니다.

### 장점

- 서로 다른 단위의 지표를 결합할 수 있습니다.
- 서울 25개 구에서 상대적으로 어디가 높은지 설명하기 쉽습니다.
- 극단값이 가중합을 완전히 지배하는 문제를 줄입니다.
- 모델 구조를 면접관과 사용자에게 비교적 쉽게 설명할 수 있습니다.

### 한계

- 절대적으로 안전하거나 위험하다는 뜻이 아닙니다.
- 비교 집단이 바뀌면 점수도 바뀝니다.
- 25개 구처럼 표본 수가 작을 때 순위 차이가 실제 차이보다 커 보일 수 있습니다.

## 10. 저표본과 결측값 처리

### 저표본 경고

최신 월 상가 거래가 기본 10건 미만이면 `low_sample_flag`를 표시합니다.

거래 건수에 따라 신뢰도를 Low, Medium, High로 구분합니다.

중요한 점은 저표본을 숨기지 않고 점수 옆에 별도 경고로 표시했다는 것입니다. 점수가 낮더라도 표본이 얇다면 강한 결론을 내리지 않습니다.

### 결측값

백분위 계산에서 유효한 값이 하나도 없으면 중립값 50을 사용합니다. 일부 값만 결측이면 유효한 값만 순위를 계산하고 결측 위치에는 50을 둡니다.

### 면접에서 말할 개선안

- 결측 사유별 처리 분리
- 저표본 지역의 베이지안 축소 또는 신뢰구간 제공
- 거래 건수에 따른 점수 불확실성 시각화
- 원점수와 백분위 점수 동시 제공

## 11. 제품 흐름과 UX 의사결정

### 화면 흐름

1. 지도 홈
2. 매물 검토
3. 3분 진단
4. 후보 비교
5. 구별 리포트
6. 판단 메모와 전문가 확인 항목

### 핵심 UX 원칙

- 추천보다 반대 근거를 먼저 보여줍니다.
- 총점만 보여주지 않고 축별 위험을 함께 보여줍니다.
- 한 후보에 고정되지 않도록 대체 후보를 제공합니다.
- 분석 결과를 복사·저장할 수 있는 메모로 전환합니다.
- 한계와 추가 확인 대상을 제품 화면 안에 직접 표시합니다.

### 상태 연결

선택한 자치구는 URL query와 `localStorage`를 통해 V2 화면 사이에서 유지됩니다.

잘못된 자치구 코드, 손상된 저장값, 브라우저 저장 차단, payload 누락, GeoJSON 실패가 발생해도 가능한 범위에서 복구 안내를 제공합니다.

## 13. 검증 전략

Redveil의 검증은 예측 모델의 정답률보다 다음 질문에 초점을 둡니다.

1. 고위험 지역은 어떤 위험 축이 겹치는지 설명되는가?
2. 애매한 지역은 즉시 탈락이 아니라 비교와 현장 확인으로 이어지는가?
3. 낮은 점수도 자동 추천처럼 과장되지 않는가?

### 고정 사례

| 사례 | 판단 | 핵심 해석 |
| --- | --- | --- |
| 서초구 예시 | 매입 보류 | 가격 부담, 거래 둔화, 변동성이 동시에 높음 |
| 송파구 예시 | 강한 비교 필요 | 일부 고위험 축이 있으나 즉시 배제보다 비교가 적절함 |
| 구로구 예시 | 추가 검토 가능 | 상대 점수는 낮지만 개별 임대차·공실 확인은 여전히 필요함 |

### 소프트웨어 검증

- Python 단위 테스트
- 공개 payload 생성 검사
- 프런트 자산 검사
- 런타임 검사
- 사이트 smoke check
- Chromium E2E
- 모바일·태블릿·데스크톱 반응형 검사

## 14. 반드시 말해야 하는 한계

Redveil은 다음을 제공하지 않습니다.

- 투자 자문이나 매수·매도 추천
- 수익률 예측
- 개별 건물의 정확한 공실률
- 임대차 계약, 권리금, 관리비, 건물 상태 판단
- 법률·세무·금융·중개 자문
- 실시간 데이터 보장
- 현장 조사와 전문가 검토의 대체

### 데이터·모델 한계

- 거래와 상권 데이터의 기준 시점이 완전히 같지 않습니다.
- 최종 점수는 구 단위라 같은 구 안의 동·블록 차이를 설명하지 못합니다.
- 공개 데이터 특성상 개별 매물의 실제 조건을 반영하지 못합니다.
- 가중치는 실증적으로 최적화한 값이 아니라 설명 가능한 1차 휴리스틱입니다.
- 백분위는 상대 점수이므로 서울 외 지역이나 다른 시점에 그대로 적용할 수 없습니다.

## 15. 면접 전에 확인할 설계 포인트

### 15.1 등급 기준과 화면 판단 기준

내부 코드의 일부 위험 등급은 35·55·75 구간을 사용하고, 공개 검증 문서의 최종 화면 판단은 45·60·75 구간을 사용합니다.

면접 전에 다음 중 하나로 설명을 정리해야 합니다.

- 내부 분석용 등급과 사용자용 판단 문구를 의도적으로 분리했다.
- 또는 두 기준을 하나로 통일하는 리팩터링이 필요하다.

현재 상태를 숨기기보다 **표현 계층 간 기준 차이를 발견했고 정합성 개선 대상으로 보고 있다**고 말하는 편이 안전합니다.

### 15.2 수요 취약성의 위치

제품 소개에는 수요 취약성이 주요 리스크 축으로 등장하지만, 현재 구 단위 최종 가중합은 거래 리스크와 점포 경쟁으로 구성됩니다.

수요 취약성은 상권 단위 별도 신호이며 공간 단위가 달라 직접 합치지 않았다고 설명할 수 있습니다. 향후에는 상권→자치구 집계 방식과 가중치 근거를 검증한 뒤 통합할 수 있습니다.

### 15.3 가중치 근거

현재 가중치는 도메인 논리와 설명 가능성을 우선한 휴리스틱입니다.

“왜 정확히 55:45인가?”라는 질문에는 임의값이라고 피하지 말고 다음처럼 답합니다.

> 1차 버전에서는 가격과 거래 가능성이 매입 의사결정의 기초라고 보고 거래 리스크를 조금 더 높게 두었습니다. 다만 학습된 최적 가중치는 아니기 때문에 민감도 분석과 전문가 검토를 통해 조정해야 합니다.

## 16. 예상 면접 질문과 답변 핵심

### Q1. 왜 이 프로젝트를 만들었나요?

공개 부동산 데이터는 많지만 사용자의 실제 판단 질문으로 번역된 제품은 적었습니다. 분석 결과를 표나 대시보드에서 끝내지 않고, 사용자가 멈추고 비교하고 기록하는 의사결정 흐름으로 만들고 싶었습니다.

### Q2. 왜 매입 추천이 아니라 보류 점수인가요?

공개 데이터만으로 개별 상가의 수익성과 적합성을 확정하기 어렵기 때문입니다. 데이터가 책임질 수 있는 범위 안에서 위험 신호와 추가 확인 대상을 제공하는 것이 더 정직하다고 판단했습니다.

### Q3. 가장 중요한 전처리는 무엇이었나요?

상가 목적에 맞는 건축물 용도 필터링, 거래가 없는 구·월까지 남기는 scaffold, 자치구 코드 표준화, 중앙값 중심 집계, 저표본 표시입니다.

### Q4. 왜 중앙값을 썼나요?

상가 거래금액은 이상치와 규모 차이가 커 평균이 대표 가격선을 왜곡할 수 있기 때문입니다.

### Q5. 왜 이동평균을 썼나요?

월별 상가 거래는 표본이 적고 변동이 커 단일 월 값만 보면 노이즈에 민감합니다. 3개월·6개월 기준선을 만들어 최근 값이 평소와 얼마나 다른지 비교했습니다.

### Q6. 왜 머신러닝을 사용하지 않았나요?

신뢰할 만한 정답 레이블과 충분한 과거 성과 데이터가 없었고, 사용 목적도 수익률 예측보다 설명 가능한 위험 검토였습니다. 이 문제에서는 불투명한 예측보다 해석 가능한 점수 구조가 적합하다고 봤습니다.

### Q7. 백분위 점수의 단점은 무엇인가요?

절대 위험 수준을 말하지 못하고 비교 집단과 시점에 따라 값이 달라집니다. 표본이 25개 구로 작아 순위 차이가 과장될 수도 있습니다.

### Q8. 저표본 문제를 어떻게 처리했나요?

최근 거래가 10건 미만이면 별도 경고를 붙이고 거래 건수에 따라 신뢰도를 구분했습니다. 점수만으로 강한 결론을 내리지 않도록 문장형 해석에도 표본 경고를 넣었습니다.

### Q9. 가중치는 어떻게 정했나요?

도메인 논리와 설명 가능성을 기준으로 한 1차 휴리스틱입니다. 검증된 최적값은 아니며 민감도 분석, 전문가 피드백, 과거 결과와의 비교가 다음 단계입니다.

### Q10. 프로젝트에서 가장 어려웠던 점은 무엇인가요?

공간 단위와 시점이 다른 데이터를 하나의 의사결정 흐름으로 정리하는 일이었습니다. 모든 데이터를 억지로 한 점수에 넣지 않고, 구 단위 최종 점수와 상권 단위 보조 신호를 구분했습니다.

### Q11. 분석 결과를 제품으로 옮길 때 무엇을 고려했나요?

점수만 보여주면 사용자가 이유를 이해하기 어렵기 때문에 위험 사유, 대체 후보, 다음 확인 항목, 메모를 함께 제공했습니다. 사용자가 빠르게 매입하도록 돕는 것이 아니라 더 신중하게 검토하도록 만드는 UX를 택했습니다.

### Q12. 다시 만든다면 무엇을 개선하겠나요?

- 데이터 시점 통일과 자동 갱신
- 행정동·블록 단위 세분화
- 저표본 불확실성 정량화
- 가중치 민감도 분석
- 전문가 검증
- 실제 과거 결과를 이용한 후향 검증
- 개별 매물 임대차·공실 데이터 연계

### Q13. 이 프로젝트에서 본인의 강점은 무엇인가요?

문제 정의, 데이터 전처리, 해석 가능한 점수 설계, 사용자 문구, 인터페이스, 배포와 검증을 하나의 제품 흐름으로 연결했다는 점입니다.

### Q14. 데이터 분석가 직무와 어떤 관련이 있나요?

서로 다른 원천 데이터를 정리하고, 비즈니스 질문에 맞는 지표를 설계하고, 분석 결과의 한계를 명시하며, 이해관계자가 행동할 수 있는 결과물로 전달하는 전 과정을 수행했습니다.

### Q15. 가장 중요한 실패 가능성은 무엇인가요?

사용자가 상대적 탐색 점수를 실제 투자 안전성이나 수익성으로 오해하는 것입니다. 그래서 추천 표현을 피하고 한계, 표본 경고, 현장 확인 항목을 반복적으로 노출했습니다.

## 19. 암기보다 이해해야 할 10문장

1. Redveil은 투자 추천 제품이 아니라 매입 전 위험 검토 제품이다.
2. 핵심 질문은 어디를 살지가 아니라 왜 멈춰야 하는지다.
3. 거래가 없는 월도 유동성 정보이므로 데이터에서 제거하지 않았다.
4. 상가 가격은 이상치가 커 중앙값을 주요 기준으로 사용했다.
5. 단위가 다른 지표를 결합하기 위해 서울 내 백분위 점수를 사용했다.
6. 거래 위험은 가격 부담, 유동성, 변동성으로 구성된다.
7. 최종 구 단위 위험은 거래 리스크와 점포 경쟁을 합친다.
8. 수요 취약성은 상권 단위의 별도 보조 신호다.
9. 낮은 점수는 추천이 아니라 남은 확인 항목이 비교적 적다는 뜻이다.
10. 결과는 점수에서 끝나지 않고 위험 사유, 대체 후보, 체크리스트와 메모로 이어진다.
